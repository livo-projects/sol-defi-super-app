# Skill — building a React/frontend app well

`interfaces/main/` is the surface users touch — your project's main web app, served at the apex `{slug}.livo.build`. (Legacy projects keep it in the singular `interface/`; everything below applies the same — just swap the root. Open the repo first to see which one this project uses.) Livo builds + hosts it on every push (mechanics: `livo://skill/building`). This skill is about **how to STRUCTURE the code** so it's maintainable, not a 600-line blob.

## Build on @livo-build/kit (it's already a dependency)
Every scaffolded interface depends on **`@livo-build/kit`** — Livo's frontend library. **Read `livo://skill/kit` for the full component/hook reference + copy-paste recipes.** Don't hand-roll wiring it already owns; import it:
- `ConnectWallet`, `LivoWeb3Provider`, `useWalletConnectors`, `WalletModal` — wallet connect (the scaffold already wires these).
- `TxButton`, `useTx`, `decodeRevert` + `ToastProvider`/`useToast` — the whole write lifecycle (pending→confirming→success/error) with toasts + explorer link. Wrap the app in `<ToastProvider>`.
- `createLivoContracts({ addresses, abis })` — bind the generated `./livo/contracts` bindings: `contracts.useRead("Counter","number")`, `<TxButton {...contracts.useContract("Counter")} functionName="increment">`.
- `useApi("/path")` (same-origin `/api/*`), `useSubgraph({ url, query })` (your indexer).
- `Address`, `Balance`, `NetworkGuard`, `TokenAmountInput`, and UI primitives `Dialog`/`Card`/`Skeleton`/`EmptyState`/`CopyButton`.
- `formatToken`/`parseToken`/`shortAddress`/`timeAgo`.

**The components are functional, NOT opinionated** — neutral defaults that inherit the app font, so projects don't all look the same. **STYLE them to match the app** (don't ship the neutral default for a real product): override CSS variables (`--wm-accent`, `--kit-accent`, …); pass a per-part `classNames` prop (great with Tailwind); target the class hooks + `[data-state]` attributes; or go fully headless on the hooks. The kit's `STYLING.md` has the full surface. Hold the rest of the app to the same bar — real modals, cards, tx toasts, loading/empty states.

## ⛔ The #1 rule: refactor, don't dump
Raw React handed to you — a pasted component, a v0/ChatGPT export, one huge `App.tsx` — is a *starting point to decompose*, NOT something to commit as-is. Split it into focused files (below) before pushing. An `App.tsx` over ~150 lines is a smell; over ~250 it's wrong. Same for code YOU write — build it decomposed from the start.

## Folder structure (Vite SPA — the default)
```
interfaces/main/src/    (legacy projects: interface/src/)
  main.tsx              app entry: mounts <App/> inside providers
  App.tsx               composition + routing ONLY — thin; renders pages
  livo/                 generated by sync_contract_bindings + scaffold_frontend — DON'T edit
    contracts.ts        typed addresses + ABIs (never hardcode an address)
    hooks.ts            typed wagmi hook per contract method
    Web3Provider.tsx, ConnectWallet.tsx, TxStatus.tsx
  components/           presentational, reusable UI (Button, Card, TokenRow…) — one per file
  pages/ (or routes/)   one file per screen/route
  hooks/                custom hooks: data fetching + stateful logic (useTokenBalance…)
  lib/ (or utils/)      pure helpers: formatting, math, constants, types.ts
```
Match the repo's existing convention before inventing one — open the main interface's `src/` first.

## Decomposition rules
- **One component per file**, named after the file.
- **Small + focused** — extract a section the moment it earns a name (three distinct sections ≈ three components).
- **Presentational vs container** — components that fetch/derive data should be thin wrappers passing plain props to dumb presentational components (reusable, testable).
- **Lift logic into custom `use*` hooks** (hooks/) — anything stateful or side-effectful (reading a balance, polling an indexer, form state, a tx flow) belongs there, not inlined. The component should read like a description of the UI, not a pile of `useState`/`useEffect`.
- **No prop-drilling past ~2 levels** — use Context. Skip Redux/Zustand/Jotai unless genuinely warranted; local state + Context covers most dApps. Chain/server state lives in TanStack Query (already present via wagmi) — don't duplicate it into useState.

## TypeScript & quality
- TS everywhere (.tsx/.ts), `strict` on; type props with an explicit `interface`/`type` (no `any`); share types from lib/types.ts.
- List keys = stable ids, never the array index when items reorder.
- `useEffect` only for real side effects (subscriptions, imperative DOM) — derive values during render instead of syncing state in an effect. Memoize only where it measurably helps.
- A11y basics: semantic elements (`<button>`, not a clickable `<div>`), `label`/`htmlFor`, alt text, focus-visible states.
- One styling approach (Tailwind / CSS modules / plain CSS — don't mix three).

## Theming — never hardcode a color, use the tokens
If the app has a theme system (`:root` + `[data-theme]`/`.dark`, Tailwind theme colors, CSS custom properties), every color in a rule must reference a token (`var(--border)`, a `text-foreground` class). A literal color (`#00ff9d`, `rgba(255,255,255,0.14)`, `bg-[#0a0a1a]`) works in the theme you wrote it in and breaks in the other (white-on-white in light mode) — the #1 "my CSS change didn't work" report. Before editing styles, grep the area for the pattern (`rgba(255,255,255`, `rgba(0,0,0`, bare `#hex` outside `:root`/`[data-theme]`) and fix **all** of them, not just the one asked about. New shade → add a token to both theme blocks.

**Always pair a foreground with its background — never set one and inherit the other.** Black text on a black background (or white-on-white, dark-on-dark) is invisible, and it happens whenever you set a `background` without also setting `color` (or vice versa) and the inherited value clashes — e.g. a dark card dropped onto a dark page, or a light button whose label stays the page's light text. Every element that sets a background must also set a readable `color` (and the reverse), using the paired tokens (`--background`/`--foreground`, `--card`/`--card-foreground`, `--wm-accent`/its on-accent text). Don't assume the default; eyeball it in BOTH themes (and in the browser spot-check) — if you can't read the text, the contrast is wrong. Aim for WCAG AA (4.5:1 for body text) at minimum.

## Native form controls only style so far
Parts of native controls render through the OS, not the DOM (a `<select>`'s open option list, date/file/color pickers, scrollbars) — CSS can't reach them. You can style the *closed* control; the popup it opens is the OS's. Themed-closed-but-stock-open is expected, not a bug to chase. When the design truly needs a themed *open* menu, build a custom button + listbox instead (keep the a11y — keyboard nav, focus, click-outside, aria) rather than piling CSS on the native element. A plain `<select>` is fine when stock styling is acceptable.

## Web3 — reuse the generated layer, don't hand-roll it
- After `deploy_contract`: `sync_contract_bindings` then `scaffold_frontend` generates `src/livo/` (typed wagmi hook per method, `ConnectWallet`, `useAuth`, `TxStatus`, `Web3Provider`, config pinned to **wagmi v3**). Import from `./livo`; never hand-write an ABI, paste an address, or rebuild a connect button.
- **Login provider:** `scaffold_frontend auth=wagmi|privy|dynamic` picks or SWITCHES it (wagmi = wallet connect, no key; privy/dynamic = email/social/embedded). App code is identical across all three via `useAuth()` + `<ConnectWallet/>`. Full guide: **livo://skill/auth**.
- Your job on top: compose those hooks inside YOUR hooks/ + components/, handle loading/error/empty states, and shape the UX.

### Web3 gotchas that bite every build — read before wiring reads/writes
- **Struct / tuple returns: access by NAME, never by index.** A view that returns a struct (e.g. `Stake { uint256 amount; uint256 lastBlock; uint256 pending; }`) is decoded by viem from the ABI: if the ABI components are *named* (almost always, for a Solidity struct) you get an **object** `{ amount, lastBlock, pending }` (each a `bigint`); only an *unnamed* tuple decodes to an array `[a, b, c]`. So `const [amount] = data` silently breaks the moment the ABI has names. Destructure by field — `const { amount, pending } = data ?? {}` — and guard `data` (it's `undefined` while loading). If you genuinely must support both shapes, normalize once: `const amount = Array.isArray(data) ? data[0] : data?.amount`. Functions returning multiple values (`returns (uint256, address)`) without names DO come back as an array — index those. When unsure, log `data` once or check the ABI in `src/livo/contracts.ts`.
- **Never hardcode a chain or assume the wallet is on it.** Contracts live on ONE chain (the deployed chain, `DEFAULT_CHAIN` in `src/livo/hooks.ts`); a wallet can be on any chain. Generated **read** hooks already pin the chain, and generated **write** hooks now pin `chainId` too — so a wrong-chain write throws a clear mismatch instead of hitting an unrelated contract at the same address. For any UI you write by hand (a raw `useReadContract`/`useWriteContract`, or a custom address), do the same: pass `chainId` and wrap the contract-interacting section in kit's `<NetworkGuard chainId={DEFAULT_CHAIN} name="Sepolia">…</NetworkGuard>` so users on the wrong network see a Switch prompt instead of a silent failure. Never paste a chain-specific address into a component — import it from `src/livo/contracts.ts`.

## Workflow
1. Read the main interface's `src/` (`interfaces/main/src/`, or legacy `interface/src/`) for the existing structure & styling.
2. Decompose the feature into pages/components/hooks — name the files first.
3. Build it decomposed; import chain access from `./livo`.
4. Ship it: small edits → push + a quick `deployment_status` + browser spot-check; a real or risky release → run the **preview→verify→promote gate** (see "Safe go-live" in `livo://skill/building`). If you touched styling, check both themes — a green build proves it shipped, not that it renders right.

## Don't
- Commit one mega-file — split it (the rule that prompted this skill).
- Hardcode a color when the app has theme tokens, or a contract address / ABI (import from src/livo/).
- Pin `"wagmi": "^2"` — let scaffold_frontend write v3 (v2 hangs the build).
- Reach for a heavy state library before local state + Context have actually failed you.
